# 生产环境参数清单

**适用**：`deploy/docker-compose.yml` + `deploy/.env`
**用法**：§1 必改 → §2 按公式算容量 → 其余保持默认 → §6 逐条检查

> 本文只讲"该填什么、为什么、怎么验"。参数含义的完整注释在 `deploy/.env.example` 里。

---

## 0. 先看这个：当前唯一的安全缺口

**平台目前的登录就是 `POST /api/v1/system/dev-login`——不校验密码，直接签发任意角色的 JWT。**

前端登录页只调这一个接口（`frontend/src/api/systemApi.ts` → `devLogin()`），
后端 `app/api/v1/system.py:27` 只检查 `settings.enable_dev_login`。

后果：**任何能访问前端页面的人，点一下登录就是 admin**（含系统管理、Key 管理）。

| 阶段 | `ENABLE_DEV_LOGIN` | 说明 |
|------|--------------------|------|
| 接 SSO / 真实账号体系**之前** | `true`（必须） | 改 false 会导致全平台无人能登录 |
| 接好之后 | `false`（立刻） | 这是上生产前的第一优先级，不是可选项 |

> 如果这个平台只在内网、且访问者都可信，可以先上；但只要"几百人"里有非运维同事，
> 在改 false 之前，任何人的浏览器收藏夹就是管理员密码。

## 1. 必改项（上线前必须动）

| 参数 | 默认值 | 生产取值 | 不改为会怎样 |
|------|--------|----------|--------------|
| `SECRET_KEY` | `please_change_me_to_random_secret` | `openssl rand -hex 32` | JWT 可被任意伪造，登录体系形同虚设 |
| `POSTGRES_PASSWORD` | `change_me_to_strong_password` | 强随机 | 数据库裸奔 |
| `REDIS_PASSWORD` | 同上 | 强随机 | 限流计数/进度 key 可被任意改 |
| `RABBITMQ_PASSWORD` | 同上 | 强随机 | 任务队列可被注入 |
| `CORS_ORIGINS` | `http://localhost` | 实际前端地址**含端口** | 浏览器报 CORS，前端调不通 API |
| `WEB_PORT` | `80` | 按实际（当前服务器口径为 `8085`） | 端口冲突或访问不到 |

> `CORS_ORIGINS` 必须精确匹配浏览器地址栏，例如 `http://10.51.13.7:8085`。
> 少写端口是最常见的踩坑点（见 nginx.conf 里"必须保留原始 Host"那段注释的同类问题）。

## 2. 容量参数（按公式算，不要拍脑袋）

### 2.1 公式

```
API 连接上限   = API_WORKERS × (DB_POOL_SIZE + DB_MAX_OVERFLOW)
Celery 连接数  = CELERY_CONCURRENCY + DEPLOY_CONCURRENCY
                 + PERF_WORKER_CONCURRENCY + 1(量化) + 1(beat)
POSTGRES_MAX_CONNECTIONS ≥ API 连接上限 + Celery 连接数 + 余量

到上游连接上限 = API_WORKERS × HTTP_POOL_MAX_CONNECTIONS
```

按当前默认值代入：

```
API 连接上限  = 2 × (20 + 30) = 100
Celery 连接数 = 4 + 2 + 2 + 1 + 1 = 10
→ POSTGRES_MAX_CONNECTIONS ≥ 110 → 取 200（已在 compose 里设默认）
```

### 2.2 逐项

| 参数 | 默认 | 什么情况下调 | 注意 |
|------|------|--------------|------|
| `API_WORKERS` | `2` | web 管理台本身接口慢、或单核 CPU 打满 | **调大必须同步调大 `POSTGRES_MAX_CONNECTIONS`**：每多 1 个 worker 多 50 条池上限 |
| `DB_POOL_SIZE`<br>`DB_MAX_OVERFLOW` | `20`<br>`30` | 一般不用动 | 网关的流式**和非流式**请求都会在等上游生成前归还连接（见 §5），这里只需覆盖"同时进行的查询数"（毫秒级），**不要按并发请求数去设** |
| `POSTGRES_MAX_CONNECTIONS` | `200` | 增加 worker 或 Celery 并发后重算 | 撞满时表现为 `FATAL: too many clients already`，API 请求直接 500 |
| `HTTP_POOL_MAX_CONNECTIONS` | `200` | 上游模型多、且确实打满 | **每个 worker 各自一份**，2 worker = 最多 400 条到上游的连接；真实有效上限由上游 vLLM 的 `--max-num-seqs` 决定，设再大也没用 |
| `HTTP_READ_TIMEOUT` | `300` | 有单次生成 > 5 分钟的场景 | 必须 **小于** nginx 的 `proxy_read_timeout`（已设 600s），否则 nginx 先掐 |

### 2.3 规模对照（几百人场景）

| 峰值同时生成 | 建议 |
|--------------|------|
| ≤ 50 | 默认值即可 |
| 50–150 | `API_WORKERS=4`，`POSTGRES_MAX_CONNECTIONS=300` |
| > 150 | 别调参了，先解决模型侧瓶颈（见交接文档 §8），并考虑 api-server 起两副本 + nginx upstream |

> **参数不是瓶径的那一天，瓶颈就是 GPU。** 交接文档实测：Qwen3.8 在 30 并发下
> TTFT 中位 25.7 秒。网关调得再好，也救不了模型的解码吞吐。

## 3. 压测相关（要用压测就得配）

| 参数 | 必填性 | 说明 |
|------|--------|------|
| `PIP_INDEX_URL` | 国内**必填** | 不配则 200MB+ 依赖拉取极慢甚至超时，perf-worker 镜像构建失败 |
| `EVALSCOPE_VER` | 建议锁 | 实测可用 `1.15.0`；不锁会随上游升级漂移（交接文档 P0） |
| `PERF_GATEWAY_API_KEY` | 经网关压测**必填** | 缺了会被网关 401，而 EvalScope 只报 `TimeoutError: Test connection failed`（毫无提示性） |
| `HF_ENDPOINT` / `USE_MODELSCOPE_HUB` | 内网必配 | `random` 数据集必须有 tokenizer |
| `PERF_TESTABLE_PROVIDER_PREFIX` | **留空** | 留空 = 不限制。填了才按前缀白名单卡 |

## 4. 不需要配的（有默认值，且 compose 未透传）

以下项改 `.env` **不会生效**（因为 compose 的 `api_env` 里没有透传），需要时走代码默认即可：

`DEBUG`、`JWT_ALGORITHM`、`DEPLOY_CONTAINER_PORT`、`DEPLOY_TGI_IMAGE`、
`GPU_STATS_TTL_SECONDS`、`PERF_REDIS_PREFIX`、`PERF_WORKER_CONCURRENCY`

> 如果确实要改其中某一项，**必须先在 `docker-compose.yml` 的 `api_env` 里加透传**，
> 否则就是在 `.env` 里写了个寂寞（这是本项目反复踩过的坑）。

## 5. 本次补上的"设了不生效"修复

之前这些参数写在 `.env` 里是**静默失效**的，已修：

| 参数 | 原来的问题 | 现在 |
|------|------------|------|
| `HIGRESS_ADMIN_API` | compose 里写死 `http://higress-gateway:8080/api` | 读 `.env`，默认值不变 |
| `AUTO_CREATE_TABLES` | compose 里写死 `"true"` | 读 `.env`，默认 `true` |
| `ENABLE_DEV_LOGIN` | compose 未透传 → 一直用代码默认 `true`，`.env` 无法关闭 | 读 `.env`，默认 `true`（保持现有行为） |
| `PERF_TESTABLE_PROVIDER_PREFIX` | compose 未透传 → 一直不限制 | 读 `.env`，默认留空 |

同时把 `backend/.env.example` 里写成 `PERF_TESTABLE_PROVIDER_PREFIX=local-` 的旧值改回留空
（与"彻底取消压测模型限制"的决策一致，原来的值会误导人以为压测只能选 local- 模型）。

## 6. 上线检查清单（逐条执行）

```bash
cd /data/llm_ops/deploy

# 1) 参数解析是否符合预期（compose 会替换 ${}，这里能看出真实值）
docker compose config | grep -E "MAX_CONNECTIONS|API_WORKERS|DEV_LOGIN|CORS"

# 2) 生效 Postgres 连接数（改 command 需要重建容器，数据在卷里不丢）
docker compose up -d postgres
docker compose exec postgres psql -U llmops -d ai_platform -c "SHOW max_connections;"
#    期望 200

# 3) 当前连接占用（远小于 200 才正常）
docker compose exec postgres psql -U llmops -d ai_platform -c \
  "SELECT count(*) AS conns, state FROM pg_stat_activity GROUP BY state;"

# 4) 重建并生效（restart 不换镜像，必须 build + up -d）
docker compose build api-server web && docker compose up -d
docker compose exec api-server python -m app.tools.check_symbols      # 期望 [OK]

# 5) 流式 + 大 body 验证（nginx SSE 参数与 20m 上限）
curl -N -s http://127.0.0.1:8085/v1/chat/completions \
  -H "Authorization: Bearer <平台Key>" -H "Content-Type: application/json" \
  -d '{"model":"<模型名>","stream":true,"messages":[{"role":"user","content":"从1数到20"}]}'
#    期望：token 逐字出现，不是攒一大段

# 6) 网关可用性 + 鉴权
curl -s http://127.0.0.1:8085/v1/models | head -c 200
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8085/v1/chat/completions \
  -H "Content-Type: application/json" -d '{"model":"x","messages":[]}'
#    期望：401（无 Key 必须被拒）
```

## 附：与本文相关的前置改动

| 改动 | 位置 | 作用 |
|------|------|------|
| nginx SSE 参数（buffering off / 600s 超时 / 20m body） | `frontend/nginx.conf` | 流式不被攒批、长回答不被 504、长上下文不 413 |
| 非流式请求提前归还 DB 连接 | `backend/app/api/v1/proxy.py` | 并发上限不再被连接池锁死为 `(20+30)×workers` |
| 主备切换重连前归还连接 | 同上 `_standby_failover` | 上游故障时不会二次占连接 |
| Postgres `max_connections=200` | `deploy/docker-compose.yml` | 避免 `too many clients already` |
