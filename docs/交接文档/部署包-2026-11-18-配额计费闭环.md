## 2. ⚠️ 覆盖前必做

### 2.1 先解到临时目录做 diff 预检

本包是**整文件覆盖**。`proxy.py` / `proxy_service.py` 等文件在工作区里还包含**之前已部署过**的改动
（流式 usage 解析、主备切换、压测隔离等），但它们在 git 里都还是未提交状态。
所以覆盖前必须核对：**打包文件与服务器现有文件的差异，应该只有本次功能**。

```bash
cd /data/llm_ops
mkdir -p /tmp/pkg-qb && cd /tmp/pkg-qb
unzip -o /path/to/quota_billing_closure.zip

# 逐文件看差异：只应出现配额/计费相关改动
for f in backend/app/api/v1/proxy.py backend/app/services/proxy_service.py \
         backend/app/services/rate_limiter.py backend/app/tasks/stats_aggregator.py \
         backend/app/main.py backend/app/models/__init__.py; do
  echo "=== $f"
  diff -u /data/llm_ops/$f /tmp/pkg-qb/$f | head -60
done
```

出现**你不认识的改动**（与配额、计费、单价、费用无关）就停手，先问清楚再覆盖。

## 7. 行为变化（可能会被问到）

| 变化 | 影响 |
|------|------|
| 不配单价 | 计 0 元，**与上线前完全一致**，不会报错 |
| 不设 `rpm_limit` / `rpd_limit` / `token_quota` | 不限制，**与上线前完全一致** |
| 新增两种 429 | `insufficient_quota`（token 用尽）、`rate_limit_error`（RPM/RPD 超限），仅对**显式设置过额度**的 Key 出现 |
| 费用页延迟 | 费用在**小时聚合**时计算，最长约 1 小时延迟（日汇总每小时刷新），不是实时到秒 |
| 改价不追溯 | 已聚合的历史小时/天是落库快照，改单价只影响之后的账单 |
| 每请求多一次写 | 非流式：`UPDATE app_key SET token_used=token_used+n`（与日志同一事务）；流式：在流结束回填时更新。单 Key 数百 QPS 时该行是轻微热点，远未到瓶颈；若将来单 Key 上千 QPS，应改为 Redis 计数 + 定期落库 |
| 压测流量不扣配额 | 与既有"压测不进报表"的隔离策略一致，否则压测会打爆真实 Key 的配额 |

## 8. 常见问题

| 现象 | 原因 / 处理 |
|------|------------|
| 页面显示 429 `insufficient_quota` | 该 Key 的 `token_used >= token_quota`。调大配额或清零：`UPDATE app_key SET token_used=0 WHERE id=<id>;`（会连带清掉历史用量，慎用） |
| 配了价但费用还是 0 | ① 还没到小时聚合时间 → 按 §5.6 手动触发；② 请求没走网关（直连模型地址不产生日志） |
| 表 `model_pricing` 不存在 | `AUTO_CREATE_TABLES=false` 且没执行 DDL → 见 §3 |
| `token_used` 与实际不符（手工清过日志） | 重新校准：`UPDATE app_key k SET token_used=COALESCE((SELECT SUM(total_tokens) FROM api_request_log l WHERE l.app_key_id=k.id),0);` |
