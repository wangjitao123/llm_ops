## 2. 压测功能（v4）— 本次核心交付

### 2.1 集成方案（已确认的决策）

| 决策项 | 结论 |
|--------|------|
| 集成方式 | **方案 A：独立 perf-worker 容器**，不改 api-server 镜像体积 |
| 压测内核 | [EvalScope](https://github.com/modelscope/evalscope) `perf`（Apache-2.0），作为依赖安装，**未 vendor 任何源码** |
| 执行模型 | Celery `perf` 队列 → `asyncio.to_thread(engine.run)` → `subprocess.Popen` → 轮询 `progress.json` → Redis |
| 中止机制 | 子进程 `terminate()` + Redis abort key |
| 默认数据集 | `random`（需 tokenizer，见 §7.1） |
| 流量隔离 | `X-Perf-Test` 头 → 网关跳过 `api_request_log`（仅经网关模式） |
| 报告 | 保留 EvalScope 原生 HTML，支持下载（见 §2.5） |
| 模型限制 | **不做限制**（默认全部可选，白名单留空 = 不放宽任何约束） |
| 指标回写模型管理 | 不做 |

### 2.5 报告下载的两种模式

| 模式 | 说明 |
|------|------|
| `?mode=summary`（**默认**） | 移除 Plotly 与全部图表，只留表格。实测 **4.55MB → 64KB**，秒开 |
| `?mode=full` | 含 12 张交互图表，把 4.5MB Plotly **内联**进 HTML（无外网也能看，但打开慢） |
| `?mode=full&offline=false` | 原始文件，保留 modelscope CDN 外链（内网会卡/白屏） |

响应头：`X-Report-Mode`、`X-Report-Charts-Removed`、`X-Report-Offline`

### 2.6 部署形态

```yaml
# deploy/docker-compose.yml 关键部分
perf-worker:
  build:
    context: ../backend
    dockerfile: ../deploy/perf/Dockerfile
    args:
      EVALSCOPE_VER: ${EVALSCOPE_VER:-}
      PIP_INDEX_URL: ${PIP_INDEX_URL:-}     # 国内必须配镜像源
  environment:
    PERF_GATEWAY_API_KEY: ${PERF_GATEWAY_API_KEY:-}   # 经网关压测必填
    HF_ENDPOINT: ${HF_ENDPOINT:-https://hf-mirror.com}
    HF_HOME: /app/perf_outputs/.cache/hf
    MODELSCOPE_CACHE: /app/perf_outputs/.cache/modelscope   # 否则容器重建要重下 tokenizer
    USE_MODELSCOPE_HUB: ${USE_MODELSCOPE_HUB:-1}
  volumes:
    - perf_outputs:/app/perf_outputs

api-server:
  volumes:
    - perf_outputs:/app/perf_outputs      # 报告下载需要读到同一份文件
```

> ⚠️ `api-server` 与 `perf-worker` **必须共享 `perf_outputs` 卷**，否则报告接口 404。

## 6. 这次踩过的坑（重要，别重复）

### 6.1 交付流程类

| 坑 | 教训 |
|----|------|
| **发了调用方没发定义方**（`gateway_service.py` 有、`gateway_repo.py` 和 `models/gateway.py` 没有） | 打包前必须跑 `python -m app.tools.check_symbols` |
| 容器 **7 周没重建**，导致 9/13~11/13 的改动一次性生效，三个问题同时爆发 | 每次部署后确认 `docker inspect <container> --format '{{.Created}}'` |
| `docker compose restart` **不换镜像** | 必须 `build` + `up -d` |
| `.env` 用 `echo >>` 追加，若末行无换行会**粘连** | 追加前 `tail -c 1 .env` 检查，或用编辑器 |
| 打包漏文件（`types/api.ts`、`router/index.ts`、`BasicLayout.vue`、`deployment_repo.py`） | 打包脚本里对每个文件 `assert os.path.exists()` |

### 6.2 代码类

| 坑 | 教训 |
|----|------|
| `httpx.AsyncClient.send()` **不接受 `timeout` 参数** | mock httpx 的测试抓不到；改用 `httpx.MockTransport` 让真实实现参与 |
| `v-model` 绑可选链 → esbuild `Invalid assignment target` | v-model 只绑确定存在的路径 |
| 静态路由写在动态路由后面 → 422 | `/models`、`/stats`、`/compare` 必须在 `/tasks/{id}` 之前 |
| `async_session_factory` 不存在 | Celery 侧统一用 `task_async_session`（NullPool，跨事件循环安全） |
| 用 `provider` 判断"是否本地模型" | **语义错误**：provider 是协议类型。压测已改为不限制 |
| 按 `status == online` 过滤可选模型 | 新建模型停在 `pending`，下拉永远空，用户无法发起首次压测 |

### 6.3 EvalScope 相关

| 现象 | 真因 |
|------|------|
| `AssertionError: Tokenizer path is required` | `random` 数据集必须有 tokenizer |
| `HTTPError 404 record not found` | tokenizer 填的仓库名在 **ModelScope**（不是 HF）上不存在 |
| `TimeoutError: Test connection failed` | 多半是 **HTTP 401**（缺 `PERF_GATEWAY_API_KEY`）；EvalScope 对非 5xx **不重试、立即失败**，报错信息毫无提示性 |
| 进度永远 0% | `progress.json` 实际在 `{work_dir}/{task_name}/` 子目录，不在根目录 |
| 日志"没动静" | 原先 `stdout=PIPE` 且只在进程结束时读；已改为写 `engine.log` 文件 |
| tokenizer 每次重下 | ModelScope 缓存在 `/root/.cache/modelscope`，不在 `perf_outputs` 卷里 → 已设 `MODELSCOPE_CACHE` |
| 报告打开卡死/白屏 | 外链 4.5MB Plotly（modelscope CDN）→ 内联后仍卡 → 最终改为默认 summary 模式 |

## 8. 压测结论（给上级/同事汇报用）

**平台侧无瓶颈，问题在模型部署本身。**

1. **Qwen3.8（10.51.13.7:8027）**：30 并发下 TTFT 中位 25.7 秒，输出吞吐仅 220 tok/s。
   - 分位分布显示第一个请求 647ms、第 5 个就 9.5 秒 → 服务端实际并发处理能力远低于 30
   - 瓶颈：**GPU 解码吞吐 220 tok/s**（7-8B AWQ/INT4 单卡正常应在 1500-3000 tok/s）

2. **MiniMax-M3（10.50.194.81:8000）**：200 并发下总吞吐 1010 tok/s，但单请求 TPOT 149ms（≈6.7 tok/s）。
   - TTFT p75 断崖到 19.5 秒 → 200 并发已饱和，合理工作点约 **100 并发**
   - 瓶颈：**单请求解码速度**，加并发只会堆总吞吐、牺牲交互体验

**改进方向**：提升单请求解码速度（加卡 / 更小模型 / 换量化方案），而非继续加并发。
检查项：`--max-num-seqs`、`--gpu-memory-utilization`、张量并行度、是否频繁 preemption。
