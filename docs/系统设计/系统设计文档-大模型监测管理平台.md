## 1. 系统概述

### 1.1 系统定位

大模型监测管理平台（以下简称"AI 网关平台"）是一个企业级大模型统一接入与管理平台，定位为**企业 AI 基础设施的管控层**。系统不直接提供大模型推理算力，而是作为统一的接入层和管理层，对接各类大模型厂商 API。

### 1.2 系统边界

| 边界 | 范围 |
|------|------|
| **系统内部** | 模型管理、Key 管理、Token 统计、统一网关、模型微调管理、模型对比、系统管理 |
| **系统外部** | 大模型厂商 API（DeepSeek、OpenAI、阿里云、百度等）、公司 SSO 系统、钉钉 |
| **不包含** | 大模型推理算力、大模型训练平台、模型评测数据集标注平台 |

### 1.3 设计约束

| 约束项 | 说明 |
|--------|------|
| 部署环境 | 企业内部网络（私有化部署），需支持容器化 |
| 技术栈 | Java 17 + Spring Boot 3.x + Vue3 + TypeScript |
| 认证方式 | 对接公司 SSO（OAuth2/SAML/LDAP），不维护独立用户体系 |
| 数据安全 | API Key 加密存储，全站 HTTPS |
| 团队规模 | 前后端开发人员合计 5-8 人 |

## 2. 系统指标估算

### 2.1 用户规模估算

| 指标 | 估算值 | 估算依据 |
|------|--------|----------|
| 企业总员工数 | 5,000 - 10,000 人 | 中型企业规模 |
| 平台注册用户数 | 200 - 500 人 | 开发者 + 管理者 + 数据科学家 |
| DAU（日活跃用户） | 50 - 150 人 | 管理端访问频率较低 |
| 活跃应用数 | 10 - 50 个 | 接入 AI 能力的业务系统 |
| 管理员数量 | 3 - 5 人 | 运维/系统管理员 |

### 2.2 API 调用量估算

| 指标 | 估算值 | 说明 |
|------|--------|------|
| 日均 API 请求量 | 1,000 万次 | 各应用调用模型 API 的总量 |
| 峰值 QPS | 5,000 | 按日均 1000 万 / 86400 × 4倍峰值系数 |
| 平均 QPS | 1,200 | 日均 1000 万 / 86400 秒 |
| 单次请求平均 Token 消耗 | 500 - 2,000 Token | 输入 + 输出 |
| 日均 Token 消耗 | 50 亿 - 200 亿 Token | 以 1000 万次 × 1000 Token 估算 |
| 月均 Token 消耗 | 1,500 亿 - 6,000 亿 Token | — |

### 2.3 管理端访问量估算

| 指标 | 估算值 |
|------|--------|
| 管理端 DAU | 50 - 150 人 |
| 管理端峰值并发 | 50 - 200 人 |
| 管理端平均页面加载要求 | < 2s |
| 统计看板刷新频率 | 30s 自动刷新 |

### 2.4 数据增量估算

| 数据类型 | 单条大小 | 日增量 | 月增量 | 年增量 |
|----------|----------|--------|--------|--------|
| 请求日志 | ~500B | ~5GB | ~150GB | ~1.8TB |
| Token 统计（小时聚合） | ~100B | ~50MB | ~1.5GB | ~18GB |
| Token 统计（天聚合） | ~100B | ~2MB | ~60MB | ~720MB |
| 操作审计日志 | ~300B | ~1MB | ~30MB | ~360MB |
| 业务数据（模型/Key/路由等） | — | ~1MB | ~30MB | ~360MB |
| **合计** | | **~5.05GB/天** | **~151GB/月** | **~1.8TB/年** |

> **注意**：请求日志占总数据量的 99% 以上，是存储规划的核心关注点。

## 3. 性能指标

### 3.1 性能目标

| 指标 | 目标值 | 测量方法 | 优先级 |
|------|--------|----------|--------|
| 网关代理延迟 | < 5ms（不含模型调用） | 压测工具（JMeter） | P0 |
| P99 网关延迟 | < 15ms | 压测工具 | P0 |
| 管理端页面加载 | < 2s（首屏） | Lighthouse | P1 |
| 统计看板刷新 | < 30s | 端到端测试 | P1 |
| API 并发处理 | ≥ 5,000 QPS | 压测 | P0 |
| 管理端并发用户 | ≥ 200 | 压测 | P1 |

### 3.2 可用性指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 系统可用性（SLA） | ≥ 99.9% | 全年宕机时间 ≤ 8.76 小时 |
| 网关可用性 | ≥ 99.95% | 多节点部署，故障自动切换 |
| RTO（恢复时间目标） | ≤ 30 分钟 | 灾难恢复时间 |
| RPO（恢复点目标） | ≤ 5 分钟 | 数据丢失容忍度 |

### 3.3 安全指标

| 指标 | 要求 |
|------|------|
| 认证方式 | 公司 SSO 统一认证 |
| 传输加密 | HTTPS（TLS 1.2+） |
| API Key 存储 | AES-256 加密存储 |
| 敏感数据脱敏 | Key 仅展示前缀 |
| 审计日志 | 关键操作 100% 记录 |
| 速率限制 | 全局 + 单 Key 两级限流 |
| 防暴力破解 | 登录失败 5 次锁定 30 分钟 |

## 4. 容量规划

### 4.1 存储容量规划

| 存储组件 | 规格 | 容量规划 | 备注 |
|----------|------|----------|------|
| **PostgreSQL / MySQL** | 主库 + 从库 | 初始 500GB，年增长 ~1.8TB | 请求日志按月分区，180 天清理 |
| **Redis** | 主从架构 | 8GB 内存 | 缓存 + 限流计数器 + 会话 |
| **消息队列** | 3 节点集群 | 100GB 磁盘 | 异步日志、任务通知 |
| **对象存储** | 可选 | 按需扩展 | 日志归档、微调数据集 |
| **ES** | 可选（二期） | 按需 | 日志全文检索 |

### 4.2 MySQL 存储明细

| 表 | 日增量 | 30 天存量 | 180 天存量 | 索引占比 |
|----|--------|-----------|------------|----------|
| api_request_log | ~5GB | ~150GB | ~900GB | ~30% |
| token_stats_hourly | ~50MB | ~1.5GB | ~9GB | ~20% |
| token_stats_daily | ~2MB | ~60MB | ~360MB | ~20% |
| audit_log | ~1MB | ~30MB | ~180MB | ~25% |
| 业务表（10+ 张） | ~1MB | ~30MB | ~180MB | ~20% |

> **建议**：请求日志表按 **月分区**，每月自动创建新分区，超过 6 个月的分区可直接 truncate 或归档。

### 4.3 带宽规划

| 链路 | 估算流量 | 建议带宽 |
|------|----------|----------|
| 网关 → 模型厂商 API | 1000 万次/天 × 平均 5KB 响应 ≈ 50GB/天 出站 | 100Mbps |
| 管理端 → 服务器 | 150 DAU × 平均 2MB/页面 ≈ 300MB/天 入站 | 10Mbps |
| 日志写入（MQ） | 1000 万条/天 × 500B ≈ 5GB/天 入站 | 10Mbps |
| **合计带宽** | | **~200Mbps（建议 1Gbps 冗余）** |

### 4.4 服务器配置建议

| 服务 | 实例数 | 配置 | 磁盘 | 备注 |
|------|--------|------|------|------|
| AI Gateway | 2-4 | 4C 8G | 40GB 系统盘 | 无状态，水平扩展 |
| API Server | 2-4 | 4C 8G | 40GB 系统盘 | 无状态，水平扩展 |
| MySQL 主库 | 1 | 8C 32G | 500GB+ SSD | 高 IOPS 要求 |
| MySQL 从库 | 1 | 8C 16G | 500GB+ SSD | 读写分离 |
| Redis 主 | 1 | 4C 8G | 40GB SSD | 纯内存 |
| Redis 从 | 1 | 4C 8G | 40GB SSD | 高可用 |
| RabbitMQ | 1-3 | 4C 8G | 100GB SSD | 集群部署 |
| Nginx | 2 | 2C 4G | 40GB 系统盘 | 负载均衡 |
| **合计（最低）** | **10-14 台** | **40C 96G** | **~1.3TB** | |

## 5. 技术选型建议

### 5.1 技术选型总表

| 层级 | 技术 | 版本 | 选型理由 |
|------|------|------|----------|
| 后端框架 | Spring Boot | 3.x | 企业级生态成熟，SSO 集成方便 |
| 网关 | 自研（Spring Cloud Gateway 封装） | — | 灵活度高，可深度定制协议转换 |
| 数据库 | MySQL | 8.0+ | 成熟稳定，满足业务需求 |
| 缓存 | Redis | 7.x | 高性能缓存 + 分布式限流 |
| 消息队列 | RabbitMQ | 3.x | 轻量可靠，运维简单 |
| 前端框架 | Vue 3 | 3.x | 组合式 API，TypeScript 支持 |
| UI 组件库 | Ant Design Vue | 4.x | 企业级 UI，组件丰富 |
| 图表 | ECharts | 5.x | 数据可视化，性能优秀 |
| 容器化 | Docker + Docker Compose | — | 部署简单，环境一致 |

### 5.2 数据库选型对比

| 对比项 | MySQL 8.0 | PostgreSQL 16 | 选型 |
|--------|-----------|---------------|------|
| 成熟度 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 持平 |
| 异步驱动 | aiomysql | asyncpg（性能更优） | PostgreSQL |
| JSON 支持 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | PostgreSQL |
| 分区表 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 持平 |
| 团队熟悉度 | ⭐⭐⭐ | ⭐⭐⭐ | 持平 |
| **结论** | 可选 | **推荐** | **PostgreSQL**（推荐 asyncpg 驱动） |

### 5.3 网关方案对比

| 对比项 | 自研（Spring Cloud Gateway） | Envoy AI Gateway | Kong AI Gateway |
|--------|------------------------------|------------------|-----------------|
| 定制灵活性 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ |
| 开箱即用 | ⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 协议转换 | ⭐⭐⭐⭐⭐（自实现） | ⭐⭐⭐（需扩展） | ⭐⭐⭐（需插件） |
| 运维复杂度 | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ |
| 社区生态 | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ |
| **结论** | **一期推荐** | 二期可选 | 二期可选 |

### 5.4 消息队列选型对比

| 对比项 | RabbitMQ | RocketMQ | Kafka |
|--------|----------|----------|-------|
| 吞吐量 | 10 万/秒 | 10 万/秒 | 100 万/秒 |
| 运维复杂度 | 低 | 中 | 高 |
| 延迟 | 微秒级 | 毫秒级 | 毫秒级 |
| 消息可靠性 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |

## 8. 风险与应对

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| 请求日志增长超出预期 | 存储成本飙升 | 中 | 提前规划日志归档，使用对象存储 |
| 模型厂商 API 不稳定 | 业务受影响 | 高 | 主备切换策略，多厂商冗余 |
| 单 Key 被盗用 | 费用超支 | 低 | 速率限制 + 用量预警 + 定期轮换 |
| 微调计算资源不足 | 任务排队 | 中 | 任务队列管理，资源优先级调度 |
| MySQL 写入瓶颈 | 日志丢失 | 低 | MQ 缓冲 + 批量写入 + 分表 |
