## 1. 系统概述

模型压测模块为平台提供 Web 化的大模型推理性能压测能力。核心是**一个独立的压测执行容器**（`perf-worker`），它消费 `perf` 队列，把平台的任务参数翻译成 EvalScope `Arguments` 并调用 `run_perf_benchmark()`，过程中回写进度，结束后把指标入库供展示与历史对比。

## 2. 系统指标

### 2.1 用户规模

| 指标 | 数值 | 说明 |
|------|------|------|
| 平台管理员 | 2-5 人 | 可发起全部压测 |
| AI 工程师 | 5-20 人 | 发起常规压测 |
| 运维人员 | 2-3 人 | 查看与中止 |
| **同时发起压测人数** | **≤ 3** | 受 perf-worker 并发上限约束（2） |

### 2.2 业务规模

| 指标 | 数值 | 说明 |
|------|------|------|
| 单任务最大并发 | 500 | `perf_max_parallel` |
| 单任务最大请求数 | 50000 | `perf_max_number` |
| 同时运行任务 | 2 | perf-worker `--concurrency=2` |
| 日压测任务数 | ≤ 20 | 非常规高频操作 |
| 单任务耗时 | 30s ~ 30min | 取决于并发与请求数 |
| 压测产生的出站流量 | 峰值约 500 并发 × 1KB/请求 ≈ 0.5 MB/s | 需关注与 api-server 的带宽竞争 |

### 2.3 性能要求

| 指标 | 要求 | 说明 |
|------|------|------|
| 列表页加载 | < 2s | 含统计卡片聚合 |
| 进度刷新延迟 | ≤ 5s | worker 回写间隔 |
| 结果入库延迟 | ≤ 10s | 压测结束后到可查询 |
| 中止生效延迟 | ≤ 10s | 从点击到 worker 停止 |
| 平台自身压测开销 | 不可测量 | 压测流量由 worker 发出，不经 API 进程 |

## 3. 容量规划

### 3.1 存储

| 表 | 估算记录数 | 单条大小 | 年增量 |
|----|-----------|---------|--------|
| `perf_task` | 20/天 × 365 ≈ 7300 | ~3KB（含结果 JSONB） | ~22MB/年 |
| `perf_task_log` | 每次任务约 50 行 × 7300 ≈ 36万 | ~200B | ~72MB/年 |

结论：**存储压力极小**，无需分区，无需归档策略。

### 3.2 计算资源

| 资源 | 需求 | 说明 |
|------|------|------|
| perf-worker CPU | 2-4 核 | aiohttp 协程，500 并发约需 2 核 |
| perf-worker 内存 | 2-4 GB | 主要是 tokenizer 加载（transformers） |
| GPU | **不需要** | 纯 HTTP 负载生成 |
| 磁盘 | 20 GB | 镜像（evalscope 依赖数百 MB）+ 临时 outputs |

### 3.3 网络

| 项 | 说明 |
|----|------|
| 出站带宽 | 峰值约 0.5-2 MB/s（取决于请求体大小） |
| **选址建议** | **独立机器最优**；若与 api-server 同机，压测高峰期可能抢占带宽导致网关延迟抖动 —— 见 ADR-002 |

## 4. 技术选型

### 4.1 压测引擎

| 候选 | 结论 | 理由 |
|------|------|------|
| **EvalScope perf** | ✅ **采用** | Apache-2.0；开环/闭环/SLA/多轮四种模式齐全；TTFT/TPOT 等 LLM 专用指标；有程序化 API `run_perf_benchmark()` |
| 自研压测脚本 | ❌ | 需要重新实现速率控制、SSE 解析、指标聚合、百分位计算，工作量远超收益 |
| locust / k6 | ❌ | 通用 HTTP 压测工具，缺 LLM 语义（TTFT/TPOT/token 吞吐），需大量二次开发 |

### 4.2 后端

| 组件 | 选型 | 理由 |
|------|------|------|
| API 框架 | FastAPI（已有） | 一致 |
| ORM | SQLAlchemy async（已有） | 一致 |
| 任务队列 | Celery + RabbitMQ（已有） | 新增 `perf` 队列 |
| 进度缓存 | Redis（已有） | `perf:progress:{id}` + `perf:abort:{id}` |
| 压测引擎 | evalscope（新增，仅 perf-worker 镜像） | 见 4.1 |

### 4.3 前端

| 组件 | 选型 | 理由 |
|------|------|------|
| 框架 | Vue 3 + Composition API（已有） | 一致 |
| UI | Ant Design Vue（已有） | 一致 |
| 图表 | ECharts（已有，`echarts` 在依赖里） | 对比柱状图、分位图 |

### 4.4 镜像与依赖隔离

**这是本模块最关键的选型约束**：

| 镜像 | evalscope | 原因 |
|------|-----------|------|
| `api-server` | ❌ 不装 | evalscope 连带 `modelscope[datasets]`、`pandas`、`nltk`、`sacrebleu`，镜像会从 ~300MB 涨到 1GB+ |
| `celery-worker` | ❌ 不装 | 同上 |
| **`perf-worker`（新增）** | ✅ 装 | 独立镜像，独立队列，崩溃不影响主链路 |

## 5. 部署架构

```
┌────────────────────────────────────────────────────────────┐
│              平台机器（部署位置：与 api-server 同机）          │
│                                                              │
│  ┌──────────────┐   ┌──────────────┐   ┌────────────────┐  │
│  │  api-server  │   │  web (nginx) │   │  perf-worker   │  │
│  │  FastAPI     │   │  Vue3 静态    │   │  evalscope     │  │
│  │  :8000       │   │  :8085       │   │  -Q perf       │  │
│  └──────┬───────┘   └──────────────┘   │  concurrency=2 │  │
│         │                               └───────┬────────┘  │
│  ┌──────▼───────┐   ┌──────────────┐           │           │
│  │  PostgreSQL  │   │  RabbitMQ    │◀──────────┘           │
│  │  perf_task   │   │  perf 队列    │                       │
│  └──────────────┘   └──────────────┘                       │
│  ┌──────────────┐   ┌──────────────┐                       │
│  │    Redis     │   │perf_outputs卷 │  HTML 报告持久化        │
│  └──────────────┘   └──────────────┘                       │
└────────────────────────────────────────────────────────────┘
              │ 压测流量（跨机单向出站 HTTP）
              ▼
┌────────────────────────────────────────────────────────────┐
│           GPU 服务器 10.51.13.7（被压测方，分属不同机器）       │
│  ┌──────────────────┐  ┌──────────────────┐                │
│  │ qwen38-multimodal│  │ qwen2.5-7b-gptq  │                │
│  │ vLLM :8027       │  │ 平台部署容器       │                │
│  └──────────────────┘  └──────────────────┘                │
└────────────────────────────────────────────────────────────┘
```

**部署要点（Q-001 已确认）**
- `perf-worker` 与 `api-server` **同机**部署，无需额外机器
- 被压测模型在 **GPU 服务器**，压测流量为**跨机单向出站** → 不存在"自己压自己"导致 API 响应抖动
- 平台机器网卡仍需承载压测出站流量（500 并发约 0.5-2 MB/s）
- **不做跨机器分布式压测**（Q-002），单机 `--concurrency=2`，并发上限 500

## 6. 监控与告警建议

| 项 | 建议 |
|----|------|
| perf-worker 存活 | 容器 restart:unless-stopped + 健康检查 |
| 任务堆积 | 队列长度 > 5 时告警（说明压测排队严重） |
| 卡死任务 | 定时巡检 `running` 超 30 分钟的任务改判 `failed` |
| worker 内存 | tokenizer 加载可能吃 1-2GB，超过 4GB 告警 |

## 7. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 压测打挂目标模型 | 业务受影响 | 并发上限 500 + 时长上限 600s + 二次确认 |
| 第三方付费 API 被压测 | 产生真实费用 | `provider` 非 `local-*` 强制二次确认（Q-005） |
| EvalScope 上游 breaking change | 平台功能失效 | 镜像内锁定版本号 |
| 同机部署抢占带宽 | 网关延迟抖动 | 建议独立机器（ADR-002） |
| worker 崩溃任务卡 running | 用户看到假运行状态 | 定时巡检超时改判 |
| `X-Perf-Test` 被伪造 | 请求不进报表 | 限流照常计数，损失可控（M04 方案3） |
