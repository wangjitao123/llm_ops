# ADR-001: 选用 Higress 作为 AI 网关

| 状态 | 已接受 |
|------|--------|
| 创建日期 | 2025-01-01 |
| 决策者 | 架构师 |
| 影响范围 | 网关层 |

## 背景

项目需要一个统一的 AI API 网关，提供路由分发、API Key 鉴权、速率限制、协议转换、请求日志等能力。需要评估自研 vs 开源方案。

## 决策

采用 **Higress AI Gateway**（阿里开源，基于 Envoy，Apache 2.0 协议）作为统一网关。

## 考虑的方案

### 方案1: Higress AI Gateway ✅
- **优点**: AI 场景原生支持、内置协议转换、活跃社区、中文文档完善、基于 Envoy 性能优异
- **缺点**: 需学习 Higress 配置体系

### 方案2: 自研 Spring Cloud Gateway
- **优点**: 完全可控、与 Java 技术栈集成好
- **缺点**: 开发工作量大（需自研鉴权/路由/限流/协议转换）、AI 场景无原生支持

### 方案3: Kong AI Gateway
- **优点**: 成熟、插件丰富
- **缺点**: 英文文档为主、AI 插件需额外付费

## 后果

- **正面**: 减少网关开发工作量 80%，开箱即用 AI 路由/协议转换/限流能力
- **负面**: 需学习 Higress 配置，二期需关注版本演进

# ADR-002: 选用 Python + FastAPI 作为后端框架

| 状态 | 已接受 |
|------|--------|
| 创建日期 | 2025-01-01 |
| 决策者 | 架构师 |
| 影响范围 | 后端服务层 |

## 背景

需要选择后端开发语言和框架，考虑因素：大模型生态、开发效率、团队招聘、性能。

## 决策

采用 **Python 3.12+ + FastAPI** 作为后端开发框架。

## 考虑的方案

### 方案1: Python 3.12 + FastAPI ✅
- **优点**: 大模型生态丰富（SDK、微调框架）、开发效率高、异步原生支持、自动 OpenAPI 文档
- **缺点**: 性能不如 Go/Java，但网关层已由 Higress 处理，后端无高并发压力

### 方案2: Java 17 + Spring Boot 3.x
- **优点**: 企业级生态成熟、性能好
- **缺点**: 大模型生态弱、代码量大、开发效率低

### 方案3: Go 1.22 + Gin
- **优点**: 性能最好、部署简单
- **缺点**: 大模型生态弱、团队招聘难

## 后果

- **正面**: 开发效率提升 40%，与大模型生态无缝衔接，微调模块可直接使用 PyTorch
- **负面**: 需要关注 Python 异步编程的最佳实践，类型安全需通过 mypy 保障

# ADR-003: 采用模块化单体架构（一期）

| 状态 | 已接受 |
|------|--------|
| 创建日期 | 2025-01-01 |
| 决策者 | 架构师 |
| 影响范围 | 整体架构 |

## 背景

需要决定一期采用微服务还是单体架构。考虑因素：团队规模、运维复杂度、业务复杂度。

## 决策

一期采用 **模块化单体（Modular Monolith）** 架构，通过 Python Package 实现模块间解耦。

## 考虑的方案

### 方案1: 模块化单体 ✅
- **优点**: 部署简单、运维成本低、开发迭代快、适合 5-8 人团队
- **缺点**: 未来拆分需一定重构成本

### 方案2: 微服务
- **优点**: 独立部署、独立扩缩容
- **缺点**: 运维复杂（需要服务发现、配置中心、API 网关）、开发调试困难

## 后果

- **正面**: 快速迭代、降低运维复杂度、模块边界清晰未来可拆分
- **负面**: 一期所有模块在同一个进程中，需要做好模块间隔离

# ADR-004: 选用 PostgreSQL 16 作为数据库

| 状态 | 已接受 |
|------|--------|
| 创建日期 | 2025-01-01 |
| 决策者 | 架构师 |
| 影响范围 | 数据层 |

## 背景

需要选择关系型数据库。考虑因素：异步驱动性能、JSON 支持、团队熟悉度。

## 决策

采用 **PostgreSQL 16** 作为主数据库，使用 `asyncpg` 异步驱动。

## 考虑的方案

### 方案1: PostgreSQL 16 + asyncpg ✅
- **优点**: asyncpg 是 Python 生态最快的异步数据库驱动，JSON 支持完善，支持分区表
- **缺点**: 团队需学习 PostgreSQL 特有语法

### 方案2: MySQL 8.0 + aiomysql
- **优点**: 团队熟悉
- **缺点**: aiomysql 性能不如 asyncpg，JSON 支持较弱

## 后果

- **正面**: 异步数据库访问性能优异，JSON 字段支持良好
- **负面**: 需学习 PostgreSQL 特有特性（如 `ON CONFLICT`、`RETURNING` 等）

# ADR-006: 请求日志异步写入 + 冷热分离

| 状态 | 已接受 |
|------|--------|
| 创建日期 | 2025-01-01 |
| 决策者 | 架构师 |
| 影响范围 | 数据层、网关层 |

## 背景

网关请求日志数据量极大（日均 5GB，1000 万行），需要设计高效的写入和存储方案。

## 决策

- 写入：Higress 输出 JSON 格式访问日志 → Filebeat 采集 → RabbitMQ → Celery 消费者批量写入 PostgreSQL
- 存储：活跃数据 30 天（热表，按月分区），归档数据 180 天（可迁移到对象存储）
- 二期：引入 Elasticsearch 或 ClickHouse 做日志存储和全文检索

## 后果

- **正面**: 异步写入不影响网关性能，批量写入降低数据库压力
- **负面**: 日志查询有 30 秒延迟（异步消费延迟），需要实现日志归档机制
