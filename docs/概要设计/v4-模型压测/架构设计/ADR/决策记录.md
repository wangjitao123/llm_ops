# ADR 决策记录 — 模型压测模块

## ADR-001: 采用 EvalScope perf 而非自研
- **决策**: 直接依赖 EvalScope perf（Apache-2.0）
- **理由**: LLM 专用指标（TTFT/TPOT/token 吞吐）开箱即用；四种压测模式齐全；有程序化 API
- **后果**: 需锁定版本；必须独立镜像（依赖体积大）
- **详情**: 架构设计文档-模型压测.md → ADR-001

## ADR-002: perf-worker 独立容器，建议独立机器
- **决策**: 新增 perf-worker 容器，`-Q perf --concurrency=2`
- **理由**: 隔离大依赖、崩溃不影响主链路、避免抢 api-server 带宽
- **后果**: 多维护一个容器；同机部署需接受带宽竞争

## ADR-003: 默认直连模型而非经网关
- **决策**: 默认直连 `model.api_base_url`
- **理由**: 测模型本身能力；且天然不污染 Token 统计，不依赖网关改造
- **后果**: 测网关开销需用户显式切换打法

## ADR-004: 压测流量完全不记录日志
- **决策**: 网关识别 `X-Perf-Test: 1` 后完全不写 api_request_log
- **理由**: 不改表结构、彻底不污染、审计由 perf_task 表满足
- **后果**: 无法从日志侧追溯压测请求；该头不可关闭

## ADR-005: 结果摘要与全量结果分列存储
- **决策**: perf_task 存摘要列 + result_json 存全量
- **理由**: 列表查询不解析 JSONB，索引友好
- **后果**: 轻微冗余换列表性能

## ADR-006: model_id 用 ON DELETE SET NULL + 冗余模型名
- **决策**: `model_id` 外键 `ON DELETE SET NULL`，同时冗余 `model_name_snapshot`
- **理由**: 压测历史有留存价值，不应因删除模型而丢失；冗余名字保证历史可读
- **后果**: 需在创建时写入快照
