## 1. 需求概述

### 1.1 需求背景
平台已有模型管理、统一网关、模型量化、模型部署能力，但**缺少性能验证手段**：
- 量化后模型是否掉性能？无数据支撑
- 部署出来的推理容器能扛多少并发？靠猜
- 调完 vLLM 参数（max-model-len / TP）效果如何？无法横向对比

业界常用 [EvalScope](https://github.com/modelscope/evalscope) 的 `perf` 子命令做压测，但它是 CLI 工具，参数多达几十项，且结果散落在本地 `outputs/` 目录，团队无法共享与回溯。

### 1.2 需求目标

| 目标类型 | 目标描述 | 衡量指标 |
|----------|----------|----------|
| 业务目标 | 为模型选型/量化/部署提供性能数据支撑 | 每个上线模型有 ≥1 次压测基线 |
| 用户目标 | 不记 CLI 参数即可发起标准压测 | 从进入页面到任务提交 ≤ 5 次点击 |
| 用户目标 | 压测结果可跨任务对比 | 支持 2-4 个任务并排对比 |
| 技术目标 | 压测不污染 Token 统计与费用报表 | 压测流量 100% 被排除 |
| 技术目标 | 压测失败不影响主链路 | perf-worker 挂掉不影响 API |

### 1.3 预期收益
- **直接收益**：量化/部署效果有数据验证，不再靠体感
- **间接收益**：容量规划有依据（知道单卡能扛多少并发）
- **管理收益**：压测历史留档，形成性能基线库

| P2 | 压测结果在本地目录，一周后就找不到了 | 高 |

### 3.2 功能详情

#### PERF-001 压测任务列表与概览
**业务规则**
- 列表列：任务名 / 目标模型 / 压测模式 / 压力参数 / 状态（含进度条）/ TTFT(P99) / 吞吐 / 操作
- 状态机：`pending`(排队) → `running`(运行中) → `completed`(已完成) / `failed`(失败) / `cancelled`(已中止)
- 顶部统计：累计任务数、成功完成数、运行中数、最近一次 TTFT(P99)
- 筛选：状态、目标模型、任务名关键字
- 运行中任务每 3 秒自动刷新进度

#### PERF-002 新建压测任务
**业务规则**
- 分 4 区：目标模型 / 压测模式 / 输入构造 / 高级设置
- 必填：目标模型、任务名称、压力参数
- 提交后进入 `pending`，由 perf-worker 消费
- 同一目标模型允许并发多个压测（但平台需限制且提示资源竞争）

#### PERF-003 模型选择与参数自动带出
**业务规则**
- 下拉数据源来自「模型管理」中 `status=online` 的模型
- 选中后自动带出 `api_base_url`、`api_key`、`tokenizer_path`（若模型有 `model_config.hf_model_id`）
- **默认打法为「直连模型」**（不污染统计）；可选「经网关」并自动注入 `X-Perf-Test: 1`

#### PERF-004 四种压测模式
| 模式 | 必填参数 | 说明 |
|------|----------|------|
| 闭环并发 | `parallel`(并发) + `number`(总请求数) | 固定并发打满 |
| 开环限速 | `rate`(RPS) + `number` | 按目标速率发 |
| SLA 自动调压 | `sla_metric` + `sla_threshold_ms` + `sla_lower_bound` + `sla_upper_bound` | 在上下界之间搜索满足 SLA 的最大压力值 |
| 多轮对话 | `parallel` + `turns` + `number_per_turn` | 带上下文 |

**业务规则**
- 并发数上限：默认 500，超过则提示（受 perf-worker 配置限制）
- 压测时长上限：默认 600 秒，超时自动中止并保留已采集数据
- SLA 模式结束条件：在 `[lower_bound, upper_bound]` 区间内搜索，返回满足 SLA 阈值的最大压力值
- ⚠️ **SLA 是「上下界搜索」而非「按步长递增」**（Phase 1 实测 EvalScope `sla_run.parse_sla_params` 后修正；原设计的"起始并发+步长"与上游能力不匹配，已改为下界/上界）

#### PERF-005 数据集与输入构造配置
**业务规则**
- **默认 `random`**：按 `input_length` / `output_length` 指定 token 数随机生成
- 其他类型：`openqa`、`speed_benchmark`、`share_gpt`、`line_by_line`、`longalpaca`
- `line_by_line` 支持上传 `.jsonl`（每行一条 prompt）
- 输入/输出 token 长度仅在 `random` 模式下生效

#### PERF-006 异步执行与实时进度
**业务规则**
- perf-worker 消费 `perf` 队列，`run_perf_benchmark()` 在子进程/线程内执行
- 进度回写：已发送数 / 总请求数、当前实际 RPS、成功率
- 进度更新频率：≤ 5 秒一次（写 Redis + DB）
- 支持中止：设置中止标志，worker 检测后优雅停止并落已采集结果

#### PERF-007 核心指标展示
**必展示**
- TTFT：均值、P50/P90/P95/P99/Max
- TPOT（每 token 输出时间）
- `output_throughput` (tok/s)、`request_throughput` (req/s)
- 成功率、成功数/总数、总耗时

#### PERF-010 历史任务对比（Must）
**业务规则**
- 选择 2-4 个已完成任务并排对比
- 对比维度：TTFT 各分位、TPOT、输出吞吐、请求吞吐、成功率、耗时
- 表格 + 柱状图双视图
- **参数差异高亮**：若两次任务参数不同（模型/并发/数据集/长度），在表头标出差异，避免误比
- 支持"同参数对比"过滤：只显示参数完全一致的任务

#### PERF-012 中止/重跑
**业务规则**
- 运行中任务可中止，状态转 `cancelled`，保留已采集数据
- 已完成/失败任务可"用相同参数重跑"（创建新任务，参数复制）

#### PERF-014 压测流量排除统计（Must）
**业务规则**
- 直连模型：不经过平台网关，天然不入统计
- 经网关：perf-worker 必带 `X-Perf-Test: 1` 请求头
- 网关识别该头后**跳过 `api_request_log` 写入**（不计 Token、不计请求数、不计费用）
- 该头由 perf-worker 强制注入，用户无法在界面上关闭（安全考虑）

## 4. 非功能需求

### 4.1 性能与容量
| 指标 | 要求 |
|------|------|
| 平台侧并发上限 | 单任务 ≤ 500 并发（可配置） |
| 同时运行任务数 | ≤ 2（perf-worker concurrency=2） |
| 进度刷新延迟 | ≤ 5 秒 |
| 指标计算 | 结果返回后 10 秒内入库可查 |

### 4.2 安全与合规
| 项 | 要求 |
|----|------|
| License 合规 | 保留 EvalScope Apache-2.0 声明，前端/文档注明来源 |
| API Key | 压测目标的 Key 不落日志、不限明文展示 |
| 权限 | 仅管理员与 AI 工程师可发起压测 |
| 滥用防护 | 并发上限 + 时长上限，防止打挂目标模型 |

### 4.3 可靠性
| 项 | 要求 |
|----|------|
| worker 隔离 | perf-worker 崩溃不影响 api-server 与主网关 |
| 任务超时 | 强制上限（默认 30 分钟），超时标记 failed |
| 结果保留 | 压测结果永久保留（可按需清理） |
