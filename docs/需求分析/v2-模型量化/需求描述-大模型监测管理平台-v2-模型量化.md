| 项目 | 内容 |

| 版本号 | v2 |
| 新增模块 | 模型量化（Quantization） |
| 对应菜单 | 模型量化 |

| 依赖工具 | PyTorch + CUDA 12.4 + llm-compressor / AutoAWQ / bitsandbytes |

## 1. 需求概述

在现有平台上新增**模型量化**功能。用户可通过平台配置量化参数，利用服务器 GPU（8×NVIDIA L20）将开源 HuggingFace 模型量化为低精度格式，量化完成后自动注册为平台新模型供后续使用。

## 2. 业界参考分析

### 2.1 现有平台怎么做量化管理

| 平台/工具 | 量化管理方式 | 可借鉴点 |
|-----------|-------------|---------|
| **HuggingFace AutoTrain** | 云端 UI：选模型→选精度→自动执行→推送到 Hub | 任务式流程、进度追踪、自动推送 |
| **Ollama / llama.cpp** | CLI + Modelfile：GGUF 量化，自己写配置 | 多种算法支持（Q4_K_M 等），参数模板化 |
| **OpenCompass** | 评测+微调一体化平台，任务队列模式 | 异步任务管理、进度条、失败重试 |
| **vLLM AWQ 集成** | 框架内直接加载 AWQ 模型，无需单独 UI | 端到端：量化→推理一条线 |
| **TensorRT-LLM** | CLI + Python API，精度+性能配置 | 支持 W4A16、W8A16、FP8 等 |
| **LMFlow** | 微调+量化平台，Web UI 操作 | 数据集管理、任务监控 |

### 2.2 量化参数通用标准

| 参数 | 业界常见值 | 说明 |
|------|-----------|------|
| 算法 | GPTQ / AWQ / bitsandbytes | GPTQ 通用性最好，AWQ 精度最优，bnb 最轻量 |
| 比特数 | W4A16（重量 4bit + 激活 16bit） | 最主流的精度组合，压缩比约 4x |
| 分组大小 | 128 / 32 / 64 | 128 是 GPTQ 默认，越小精度越高但模型越大 |
| 校准数据 | 128~256 条文本 | wikitext / c4 / 自定义 |
| W4A16 | 4bit 权重 + 16bit 激活 | 绝大多数场景推荐 |
| W8A16 | 8bit 权重 + 16bit 激活 | 几乎无损，压缩比 2x |

### 2.3 量化后模型管理常见做法

| 做法 | 说明 |
|------|------|
| 模型保存为 HuggingFace 格式 | 用 `save_pretrained()`，框架无关 |
| 自动注册到模型库 | 量化完成后平台自动创建 Model 记录 |
| 量化配置元数据 | 在模型配置中记录算法、精度等，方便追溯 |
| 共享存储 | 所有量化模型放在共享卷 `/models/` 下 |
| 模型版本标记 | 版本号含量化信息：`1.0-q4a16-gptq` |

## 3. 原型对比分析

### 3.1 我的原型 vs 业界实践对比

| 模块 | 我的原型 | 业界标准做法 | 结论 |
|------|---------|-------------|------|
| **任务列表** | 表格：名称、基座模型、量化方案、状态、进度、操作 | ✅ 一致，行业通用模式 | ✅ **通过** |
| **创建弹窗** | 任务名、HF ID、算法、精度、分组、校准样本 | 还常见「数据集选择」「输出格式」选项 | ⚠️ 缺少「校准数据集」选择 |
| **进度展示** | 百分比进度条 | ✅ 标准做法，vLLM/LMFlow 也这样 | ✅ **通过** |
| **任务操作** | 详情/提交/取消/删除 | 还有「重试失败任务」「下载量化模型」 | ⚠️ 缺少「重试」和「下载」 |
| **结果注册** | 自动创建平台 Model | ✅ 必要功能 | ✅ **通过** |
| **量化参数模板** | 无预设模板 | 业界常用「快速模板」：W4A16-GPTQ、W4A16-AWQ | ⚠️ 缺少常用方案一键选择 |
| **模型详情页联动** | 无 | 模型详情页应显示「来源量化任务 ID」 | ⚠️ 缺少双向追溯 |
| **GPU 资源监控** | 无 | 部分平台在任务详情显示 GPU 使用率 | 可选，优先级低 |

## 4. 核心角色与交互流程

### 用户角色
- **平台管理员**：创建、查看、管理量化任务
- **GPU Worker**（系统）：自动执行量化并将结果注册回平台

### 主流程
```
管理员 → 创建任务（选模型/配参数/选数据集）
       → 提交执行 → GPU Worker 下载模型
       → 执行量化 → 保存到共享卷
       → 更新进度 → 注册模型
       → 完成 → 管理员在模型管理中看到新模型
```

## 5. 技术约束

- GPU Worker 使用独立 Docker 镜像（pytorch/pytorch:2.4.0-cuda12.4-cudnn9-runtime）
- 量化模型保存到 Docker 共享卷 `quantized_models:/models`
- 队列名 `quantization`，与主 Celery worker 隔离，防止阻塞常规任务
- 单次量化超时上限 3 小时（7B 模型约 15~30 分钟，70B ~ 2 小时）
