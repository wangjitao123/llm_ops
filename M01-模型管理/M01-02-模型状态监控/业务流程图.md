## 流程说明

### 1. 心跳检测循环（主流程）

心跳检测是一个持续运行的后台守护进程，以 30 秒为周期对每个已启用的模型进行健康检查。

| 步骤 | 操作 | 执行者 | 说明 |
|------|------|--------|------|
| 1 | 遍历所有已启用模型 | 心跳守护进程 | 每次循环开始时获取最新模型列表 |
| 2 | 发送心跳请求 | 心跳守护进程 | 向模型 API 发送 HTTP GET/HEAD 请求 |
| 3 | 记录响应时间 | 心跳守护进程 | 计算请求往返延迟 |
| 4 | 判定状态 | 心跳守护进程 | 根据延迟阈值判定：< 500ms 在线，500ms~2s 高延迟，> 2s 严重延迟 |
| 5 | 连续失败计数 | 心跳守护进程 | 请求失败时递增，成功时重置 |
| 6 | 离线判定 | 心跳守护进程 | 连续 3 次失败判定为离线 |
| 7 | 状态变更检测 | 心跳守护进程 | 对比当前状态与上次状态，只有变更时才触发通知 |
| 8 | 等待 30 秒 | 心跳守护进程 | 进入下一轮检测周期 |

### 2. 状态判定规则

| 状态 | 判定条件 | 说明 |
|------|---------|------|
| 在线 | 心跳成功且响应时间 < 500ms | 正常服务状态 |
| 高延迟 | 心跳成功且响应时间 500ms~2s | 服务质量下降，需关注 |
| 严重延迟 | 心跳成功且响应时间 > 2s | 服务质量严重下降，持续 5 分钟触发告警 |
| 离线 | 连续 3 次心跳失败 | 模型不可用，触发告警并停止路由 |
| 待配置 | 模型已接入但未完成初始化 | 初始状态，需要进行连通性测试 |

### 3. 状态变更与通知

| 状态变更 | 触发动作 | 通知方式 |
|---------|---------|---------|
| 在线 → 高延迟 | 记录日志 | 不通知（仅标记） |
| 在线 → 严重延迟 | 持续 5 分钟触发告警 | 钉钉推送 |
| 在线 → 离线 | 立即触发告警 | 钉钉推送 + 停止路由 |
| 高延迟 → 在线 | 记录日志 | 不通知 |
| 离线 → 在线 | 触发恢复通知 | 钉钉推送 |
| 离线 → 高延迟 | 触发恢复通知 | 钉钉推送 |

## 告警通知内容

### 离线告警消息示例

```
⚠️ 模型离线告警

模型名称：DeepSeek-V3
离线时间：2025-01-15 14:30:22
连续失败次数：3
处理建议：请登录平台检查模型配置或联系厂商
```

### 严重延迟告警消息示例

```
🔴 模型严重延迟告警

模型名称：GPT-4o
当前延迟：3500ms
持续时间：5分钟
阈值：2000ms
处理建议：请登录平台查看详情或切换备用模型
```

### 恢复通知消息示例

```
✅ 模型恢复通知

模型名称：DeepSeek-V3
恢复时间：2025-01-15 14:35:10
当前延迟：120ms
状态：在线
```

## 异常处理

| 异常场景 | 处理方式 |
|----------|----------|
| 模型连续 3 次心跳失败 | 标记为离线，触发告警，停止路由到该模型 |
| 模型响应时间连续 5 分钟 > 2s | 标记为严重延迟，触发告警 |
| 心跳守护进程自身异常 | 独立监控守护进程，自动重启 |
| 模型自动恢复 | 状态更新为在线，发送恢复通知 |
| 短时间内频繁状态切换 | 引入防抖机制，状态稳定 30 秒后再触发通知 |
